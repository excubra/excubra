# ADR-0012: Webhook delivery — HMAC, retry, idempotency

Status: accepted · Date: 2026-09-05

## Context

The contract v1 (salt: "Schnittstelle EX0 → CRM") promises at-least-once delivery
with HMAC signatures, exponential backoff up to 24 hours, visible delivery state, and
idempotency via `event_id`. The receiver must be able to build against fixtures before
the first real event.

## Decision

**Targets.** `webhook_targets`: id, name, URL (https required unless the host is a
private/overlay address), secret (32 random bytes, shown once, stored encrypted-at-rest
is *not* a goal — the file is on the server that signs with it), scope (`tenant_id` or
`*`), enabled flag. A target with scope `*` receives every tenant's events — that is
the VIICO CRM.

**Fan-out.** When an event is stored, one `deliveries` row per matching target is
created in the same transaction, in the event's day file (ADR-0005), with the
**serialised body stored as text**. Retries re-send those exact bytes; the signature
covers `timestamp + "." + body`, so a byte-identical body is a requirement, not an
optimisation.

**Request.** `POST <url>`, `Content-Type: application/json`, `User-Agent:
excubra/<version>`, headers:

- `X-EX0-Event-Id: <event_id>`
- `X-EX0-Timestamp: <unix seconds of this attempt>`
- `X-EX0-Signature: sha256=<hex(HMAC-SHA256(secret, timestamp + "." + body))>`

Timeout 10 s, no redirects followed, response body ignored beyond 1 KiB.
`2xx` = delivered. Anything else, including timeouts, = failed attempt.

**Backoff.** Attempts at +30 s, +1 m, +2 m, +5 m, +10 m, +30 m, +1 h, then hourly, until
24 h after `occurred_at`; then the delivery is `failed` and the console shows it with the
last status and error. A worker polls due deliveries every 5 s from today's and
yesterday's day files, 8 in flight, one in flight per target (ordering within a target
is still not guaranteed and the contract says so).

**Idempotency.** The receiver deduplicates on `X-EX0-Event-Id` / `event_id`. EX0 never
reuses an id, and a retry carries the same id and body.

**Test.** `POST /v1/webhooks/{target_id}/test` (status API) and the console button
create a real `test.ping` event scoped to the target only and deliver it through the
same worker — no special path.

**Fixtures.** `fixtures/events/<type>.json` — one full webhook body per event type,
plus `fixtures/events/README.md` with the test secret `ex0-test-secret`, a fixed
timestamp `1757000000`, and the resulting signature for each file. They are
generated by a test (`go test ./internal/server/webhook -update`) so they cannot drift
from the code.

## Consequences

- Delivery state lives beside the event; retention removes both together.
- A receiver that answers `5xx` for a processing error triggers retries — the contract
  tells it to answer `2xx` and process asynchronously.

## Rejected

- Signing only the body without a timestamp: replayable forever.
- Persistent queue outside SQLite: another service.
- Per-target ordering guarantees: would require a single in-flight per target *and*
  head-of-line blocking through failures; the contract explicitly uses `since` instead.
